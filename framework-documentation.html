🎨 Design Patterns Implemented

1. Page Object Model (POM)

Purpose: Encapsulate page elements and actions in dedicated classes

Benefits: Reduces code duplication, improves maintainability, separates test logic from page details

Example:

export class LoginPage extends BasePage {
  private readonly emailInput: Locator;
  private readonly passwordInput: Locator;
  private readonly loginButton: Locator;

  async login(email: string, password: string): Promise<void> {
    await this.fill(this.emailInput, email);
    await this.fill(this.passwordInput, password);
    await this.click(this.loginButton);
  }
}

2. Singleton Pattern

Purpose: Ensure only one instance of a class exists

Used In: BrowserManager, Logger, ConfigReader, TestDataFactory

Example:

export class BrowserManager {
  private static instance: BrowserManager;
  
  private constructor() {}
  
  public static getInstance(): BrowserManager {
    if (!BrowserManager.instance) {
      BrowserManager.instance = new BrowserManager();
    }
    return BrowserManager.instance;
  }
}

💡 Interview Tip

Q: Why use Singleton for BrowserManager?

A: To ensure we have only one browser instance throughout test execution, preventing resource wastage and ensuring consistent browser state. This also provides a centralized point for browser configuration and management.

3. Factory Pattern

Purpose: Create objects without specifying exact class

Used In: TestDataFactory for generating test data

Example:

export class TestDataFactory {
  createUser(overrides?: Partial<UserData>): UserData {
    return {
      firstName: faker.person.firstName(),
      lastName: faker.person.lastName(),
      email: faker.internet.email(),
      password: this.generateSecurePassword(),
      ...overrides
    };
  }
}

// Usage
const user = testDataFactory.createUser({ email: 'custom@example.com' });

4. Fluent Interface Pattern

Purpose: Enable method chaining for readable code

Benefits: Improves code readability, creates DSL-like syntax

Example:

// Methods return 'this' for chaining
async enterEmail(email: string): Promise<LoginPage> {
  await this.fill(this.emailInput, email);
  return this;
}

// Usage
await loginPage
  .goto()
  .then(lp => lp.enterEmail('test@example.com'))
  .then(lp => lp.enterPassword('password123'));

5. Template Method Pattern

Purpose: Define skeleton of algorithm in base class

Used In: BasePage provides template methods for all page objects

Example:

export abstract class BasePage {
  // Template methods available to all page objects
  async click(locator: Locator): Promise<void> {
    await this.waitForElement(locator);
    await locator.click();
  }
  
  async fill(locator: Locator, text: string): Promise<void> {
    await this.waitForElement(locator);
    await locator.fill(text);
  }
}

6. Component Pattern

Purpose: Create reusable UI components

Benefits: Composition over inheritance, reusability

Example:

export class Header {
  async search(query: string): Promise<void> {
    await this.searchBox.fill(query);
    await this.page.keyboard.press('Enter');
  }
}

// Compose into page objects
export class DashboardPage extends BasePage {
  public readonly header: Header;
  
  constructor(page: Page) {
    super(page);
    this.header = new Header(page);
  }
}

7. Fixture Pattern

Purpose: Setup and teardown automation

Benefits: Reduces boilerplate, ensures consistent test setup

Example:

export const test = base.extend<CustomFixtures>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);
    await use(loginPage);
  },
  
  authenticatedPage: async ({ page }, use) => {
    // Auto-login before test
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await loginPage.login('user@example.com', 'password');
    await use(page);
  }
});

🔧 Framework Components

Core Components

BasePage.ts

Purpose: Abstract base class providing common page interactions

Key Methods:

  • click(locator) - Click with built-in wait
  • fill(locator, text) - Fill input field
  • waitForElement(locator) - Smart wait for element
  • getText(locator) - Get element text
  • isVisible(locator) - Check visibility
  • takeScreenshot(name) - Capture screenshot

BrowserManager.ts

Purpose: Singleton for browser instance management

Features:

  • Single browser instance across tests
  • Multiple browser context support

Writing Tests

UI Test Example

import { test, expect } from '../fixtures/testFixtures';
import { testDataFactory } from '@core/TestDataFactory';

test('should login successfully', async ({ loginPage, page }) => {
  // Arrange
  const user = testDataFactory.createUser({
    email: 'demo@example.com',
    password: 'Demo@123'
  });

  // Act
  await loginPage.goto();
  await loginPage.login(user.email, user.password);

  // Assert
  await expect(page).toHaveURL(/dashboard/);
});

API Test Example

import { ApiHelper } from '@utils/ApiHelper';

test('should create user via API', async () => {
  // Arrange
  const api = new ApiHelper('https://api.example.com');
  const newUser = testDataFactory.createUser();

  // Act
  const response = await api.post('/users', newUser);

  // Assert
  await api.verifyStatus(response, 201);
  const createdUser = await api.getResponseJson(response);
  expect(createdUser.email).toBe(newUser.email);
});

✨ Best Practices

1. Use Page Objects

Always encapsulate page interactions in page objects. Never interact with elements directly in tests.

// ❌ Bad
await page.locator('#email').fill('test@example.com');

// ✅ Good
await loginPage.enterEmail('test@example.com');

2. Avoid Hard Waits

Use smart waits from BasePage instead of arbitrary timeouts.

// ❌ Bad
await page.waitForTimeout(5000);

// ✅ Good
await this.waitForElement(locator);

3. Use Test Data Factory

Generate realistic test data instead of hardcoding values.

// ❌ Bad
const email = 'test123@example.com';

// ✅ Good
const user = testDataFactory.createUser();

4. Leverage Fixtures

Use custom fixtures for common setup/teardown operations.

// ✅ Good - Auto-authenticated
test('should access dashboard', async ({ authenticatedPage }) => {
  // Already logged in!
  await authenticatedPage.goto('/dashboard');
});

5. Keep Tests Independent

Each test should run standalone without depending on others.

6. Use Descriptive Names

Test and method names should clearly describe what they do.

// ❌ Bad
test('test1', async () => { ... });

// ✅ Good
test('should display error message for invalid credentials', async () => { ... });

7. Log Important Actions

Use Logger for debugging and tracking test execution.

logger.info('Starting login test');
logger.error('Login failed', { error: errorMessage });

8. Handle Errors Gracefully

Capture screenshots on failure for debugging.

try {
  await loginPage.login(email, password);
} catch (error) {
  await loginPage.takeScreenshot('login-failure');
  throw error;
}

🎤 Interview Preparation Guide

Framework Overview Questions

Q: Can you explain your framework architecture?

A: "I've built a layered Playwright TypeScript framework with 4 main layers: Test Layer (test scenarios), Page Object Layer (page interactions), Core Layer (base classes), and Utility Layer (helpers). This separation ensures maintainability and scalability."

Design Pattern Questions

Q: What design patterns did you implement?

A: "I implemented 7 design patterns:

  • Page Object Model - For clean test structure
  • Singleton - For BrowserManager and utilities
  • Factory - For test data generation
  • Fluent Interface - For readable method chaining
  • Template Method - In BasePage for common operations
  • Component - For reusable UI components
  • Fixture - For setup/teardown automation

Each pattern solves a specific problem and together they create a robust framework."

Technical Questions

Q: How do you handle waits in your framework?

A: "I use smart waits in the BasePage class. Every interaction method (click, fill, etc.) has built-in waitForElement() that waits for visibility. This eliminates flaky tests from timing issues and avoids hard waits."

Test Data Questions

Q: How do you manage test data?

A: "I use the Factory pattern with Faker.js in TestDataFactory. It generates realistic data on-demand with methods like createUser(), createAddress(), etc. This ensures unique data for each test run and supports data-driven testing."

Reporting Questions

Q: What reporting mechanisms do you have?

A: "The framework supports multiple reporters: HTML (built-in Playwright), JSON (for parsing), JUnit (for CI/CD integration), and Allure (for detailed reports with screenshots and videos). All configured in playwright.config.ts."

CI/CD Questions

Q: How is your framework integrated with CI/CD?

A: "I've set up GitHub Actions workflow that runs tests on push/PR, executes across multiple browsers in parallel, uploads test artifacts and reports, and has scheduled daily runs. The framework is also Dockerized for consistent execution."

Scalability Questions

Q: How does your framework scale?

A: "The framework scales through:

  • Parallel execution (configured workers)
  • Modular page objects (easy to add new pages)
  • Reusable components (composition pattern)
  • Environment-based configuration (dev, qa, prod)
  • Path aliases in TypeScript (clean imports)

Adding new tests or pages follows the same pattern, ensuring consistency."
