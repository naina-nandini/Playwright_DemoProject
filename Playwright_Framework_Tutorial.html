Mastering Playwright Automation

A Deep Dive into Page Object Model (POM), Fixtures, and Framework Architecture

The Challenge: Why do we need a Framework?

When you first start writing automation, you might write "raw" scripts where you find an element and click it directly in the test file. However, as your project grows to hundreds of tests, this becomes a nightmare because:

  • Duplication: You select the same "Login Button" in 50 different files. If the ID changes, you fix 50 files.
  • Readability: Test logic gets buried under technical implementation details (selectors like div > span:nth-child(3)).
  • Flakiness: Without centralized waiting and handling, tests become unstable.
🏗️

Page Object Model (POM)

Separates the structure of the page (HTML elements) from the business logic (Tests). The page details live in a dedicated class.

🔧

Fixtures

Playwright's unique power. It handles Setup and Teardown automatically and injects page objects directly into your tests.

⚙️

Utilities

Shared helpers like Loggers, data generators, or API wrappers that keep your code DRY (Don't Repeat Yourself).

1. The Foundation: Page Object Model (AlertsPage.ts)

Instead of writing selectors in our test, we create a class that represents the "Alerts Page". This class encapsulates everything about that page.

Key Principle: The test should say "Trigger Alert" (Intent), not "Click button with ID xyz" (Implementation). 
export class AlertsPage extends BasePage {
    // 1. Private Locators (Encapsulation)
    private get alertButton(): Locator { 
        return this.page.locator("button[onclick='alertbox()']"); 
    }

    // 2. Public Actions (The only thing tests can see)
    async triggerSimpleAlert(): Promise<void> {
        await this.click(this.alertButton); // Uses a helper wrapper
        logger.info('Triggered simple alert'); // Built-in logging
    }
}

2. The Glue: Custom Fixtures (testFixtures.ts)

In standard Playwright, you get a page fixture. But we want an initialized alertsPage ready to use! We extend standard test to include our own objects. 

export const test = base.extend<CustomFixtures>({
    // 1. Define the fixture name 'alertsPage'
    alertsPage: async ({ page }, use) => {
        // 2. Setup Phase: Create logic before test
        const alertsPage = new AlertsPage(page);
        await alertsPage.goto(); // Auto-navigate!

        // 3. Pass it to the test
        await use(alertsPage);

        // 4. Teardown Phase (Optional): Runs after test
        // e.g., await alertsPage.cleanup();
    },
});

3. The Result: The Clean Test (AlertsPracticePOM.spec.ts)

Because we did the hard work in the POM and Fixture files, look how simple and readable our test file becomes. It reads like plain English instructions.

1
Import Fixed: We import test from our custom fixture file, not just default playwright.
import { test } from '../fixtures/testFixtures';
2
Dependency Injection: We ask for { alertsPage } in the test arguments, and Playwright gives it to us already initialized and navigated! 
test('Simple Alert', async ({ alertsPage, page }) => {
    // 1. Action: High-level method call
    await alertsPage.switchToOkTab();

    // 2. Assertion: Listen for dialog event
    page.on('dialog', async dialog => {
        expect(dialog.type()).toBe('alert');
        await dialog.accept();
    });

    // 3. Trigger
    await alertsPage.triggerSimpleAlert();
});

Summary of Benefits

By using this structure in your AlertsPracticePOM.spec.ts, you have achieved:

  • Maintainability: If the "Alert Button" ID changes, you change it in one place (AlertsPage.ts), and all tests update automatically.
  • Reliability: The BasePage (which AlertsPage extends) likely contains smart wait logic to prevent flaky tests.
  • Traceability: The Logger utility records every action (Navigated, Clicked, Triggered) automatically, making debugging failures easy.
  • Scalability: You can add 100 more tests using alertsPage without duplicating setup code.
